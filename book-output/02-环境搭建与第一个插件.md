## 2.1 环境准备

在写任何代码之前，先确保你的机器上已有以下工具。

### Node.js（版本 18+）

DeepSeek Harness 是一个 Node.js 应用，你需要 Node.js 18 或更高版本。推荐使用 20 LTS 或 22 LTS。

检查版本：

```sh
node -v
# 输出示例：v20.18.0
```

如果版本低于 18，请到 [nodejs.org](https://nodejs.org) 下载最新 LTS 版本。

> **小提示**：建议用 `nvm`（Node Version Manager）管理 Node 版本，方便在项目之间切换。安装后运行 `nvm install 20` 即可。

### pnpm

Harness 使用 pnpm 作为包管理器，因为它的 monorepo 支持最好。

安装 pnpm：

```sh
npm install -g pnpm
```

检查版本：

```sh
pnpm -v
# 输出示例：9.15.4
```

### 推荐编辑器：VS Code

虽然不是必须的，但 VS Code 加上 TypeScript 插件能提供最好的开发体验——自动补全、类型检查、跳转定义，这些在写插件时非常有用。

**可选的 VS Code 扩展：**
- **TypeScript + JavaScript**（内置，确保已启用）
- **YAML**（Red Hat 出品，编辑 `cordis.yml` 时语法高亮）
- **ESLint**（如果仓库配置了 lint）

### 本节小结

你已确认机器上有 Node.js 18+ 和 pnpm。这是 Harness 开发的基础，后面所有操作都依赖它们。

## 2.2 获取 Harness 源码

### 克隆仓库

从 GitHub 克隆 DeepSeek Harness 仓库：

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
```

如果你还没有配置 GitHub SSH，也可以用 HTTPS 方式。

### 安装依赖

```sh
pnpm install
```

这一步做了三件事：

1. **解析依赖**：pnpm 读取根目录的 `package.json` 和各个子包的 `package.json`，搞清楚整个 monorepo 需要哪些依赖。
2. **下载包**：从 npm registry 下载所有第三方依赖（React、Vite、Cordis 框架等），放到 `node_modules` 中。
3. **链接工作区包**：pnpm 把仓库内各子包（`packages/core`、`packages/llm` 等）互相链接起来，让它们可以像外部包一样相互 `import`。

这个过程可能需要一两分钟，取决于网络状况。如果中途失败，通常是网络问题，重试 `pnpm install` 即可。

### 构建项目

安装完成后，需要构建一次以获得可运行的 CLI：

```sh
pnpm run build
```

构建会编译 TypeScript 源码、打包前端资源、生成 CLI 的可执行入口。第一次构建会久一些（约 1-3 分钟），后续增量构建会快很多。

### 验证：检查 CLI 是否可用

```sh
pnpm dsh --version
```

你应该能看到类似 `0.0.0` 或具体版本号的输出。如果能看到版本号，说明环境搭建成功，Harness 已经可以运行了。

> **常见问题**：如果 `pnpm dsh --version` 报错 `command not found`，说明构建没有成功完成。重新运行 `pnpm run build` 并检查输出中是否有错误信息。

### 本节小结

你已成功克隆、安装依赖、构建并通过 `pnpm dsh --version` 验证了 Harness CLI。现在环境可以用了。

## 2.3 项目结构概览

在开始写插件之前，快速了解仓库布局——这样你就知道"东西放在哪"。

```
deepseek-harness/
├── apps/               # CLI 应用入口
│   └── cli/            # dsh 命令行工具
├── packages/           # 所有插件包和核心库
│   ├── core/           # 核心服务（会话、工具、Agent 生命周期）
│   ├── llm/            # LLM 适配器
│   ├── shell/          # Shell 执行能力
│   ├── fs/             # 文件系统操作
│   ├── web/            # Web UI
│   └── ...             # 其他 50+ 包
├── vendor/             # 第三方依赖的 vendor 版本
│   └── cordis/         # Cordis 插件框架（Harness 的底层框架）
├── docs/               # 文档
├── scripts/            # 构建和辅助脚本
└── package.json        # monorepo 根配置
```

关键目录就这几个：

- **`apps/`** — 存放 CLI 应用。正常情况下你不需要动这里，除非你要改 `dsh` 命令本身。
- **`packages/`** — 这是插件的宝库。所有内置功能（shell 执行、文件操作、LLM 接入等）都放在这里。它们是 Cordis 插件的真实例子，你写插件时可以借鉴它们的写法。
- **`vendor/`** — 存放 Cordis 框架的 vendor 副本。Cordis 是 Harness 的底层插件框架，第 3 章会深入介绍。
- **`docs/`** — 文档资源。

> **暂时不需要深入了解每个目录**。你只需要知道：写好的插件放在 `scratch-plugin/`（我们马上创建），框架在内置的 `packages/` 里，想找参考代码就去 `packages/` 翻。

### 本节小结

你了解了仓库的整体布局，知道 CLI 在 `apps/`、内置插件在 `packages/`、框架在 `vendor/cordis/`。

## 2.4 第一个插件（hello-plugin）

这是全书最重要的动手环节。你会创建一个最小插件，让它被 Harness 加载并打印一条消息。

### 步骤 1：创建插件目录

在仓库根目录创建 `scratch-plugin/src/` 目录：

```sh
mkdir -p scratch-plugin/src
```

为什么叫 `scratch-plugin`？因为这只是临时练习用的目录，不提交到仓库。`src` 是放 TypeScript 源文件的标准位置。

### 步骤 2：编写插件代码

创建 `scratch-plugin/src/index.ts`，写入以下内容：

```ts
// 导入 Context 类型。Context 是 Cordis 框架的核心抽象——它代表
// "插件的运行环境"。所有插件能力都通过 ctx 对象暴露。
import type { Context } from '@deepseek-ai/cordis'

// name 是插件的显示名称，用于日志和诊断信息中标识这个插件。
// 它是可选的，但强烈建议提供，否则调试时只能看到匿名插件。
export const name = 'hello-plugin'

// apply 是插件的入口函数。Cordis 在加载插件时调用它，
// 并将上下文对象（ctx）作为参数传入。
// 注意：apply 可以返回 void 或 Promise<void>（支持异步初始化）。
export function apply(ctx: Context) {
  // 这里就是你写插件逻辑的地方。
  // 在 apply 执行时，插件声明依赖的所有服务（如果有的话）都已就绪。
  // 目前这个插件不依赖任何外部服务，所以只打印一条日志。
  console.log('[hello-plugin] plugin loaded!')
}
```

**代码解读：**

- `import type { Context } from '@deepseek-ai/cordis'` — 只导入类型，运行时不会有这个 import。`Context` 是框架的核心接口。
- `export const name = 'hello-plugin'` — 导出一个字符串常量作为插件名。在日志中你会看到这个名字。
- `export function apply(ctx: Context)` — 插件入口。框架加载插件时调用此函数。`ctx` 是操作手柄——你通过它注册事件监听、工具、服务等。

> **注意**：这个文件不包含任何"启动服务器"或"创建应用"的代码。插件只描述自己贡献什么，加载和生命周期由框架管理。这是 Cordis 的核心思想。

### 步骤 3：创建 patch 配置文件

Harness 通过 YAML 配置文件来组装插件。这种配置文件叫做 **patch**，它告诉框架"加载哪些插件以及怎么配置它们"。

创建 `scratch-plugin/cordis.yml`：

```yaml
- insert:
    - id: hello
      name: '/绝对路径/到/deepseek-harness/scratch-plugin/src/index.ts'
```

把 `/绝对路径/到/deepseek-harness` 替换为你的仓库实际路径。比如你的仓库在 `/home/user/deepseek-harness`，那么 `name` 就是 `/home/user/deepseek-harness/scratch-plugin/src/index.ts`。

> **为什么必须用绝对路径？** patch 文件只贡献配置，不会改变加载器解析模块时使用的基准目录。用相对路径会导致加载器找不到你的文件。这是新手最容易踩的坑。

**快速获取绝对路径：**

```sh
# 在仓库根目录运行
pwd
# 复制输出的路径，拼上 /scratch-plugin/src/index.ts
```

### 步骤 4：启动并验证

用 `--patch` 参数启动 Web UI，传入你的 patch 文件：

```sh
pnpm dsh web --patch ./scratch-plugin/cordis.yml
```

观察终端输出。在启动日志中，你会看到类似这样的内容：

```
[hello-plugin] plugin loaded!
```

**如果看不到这条消息，检查以下三项：**

1. `scratch-plugin/cordis.yml` 中的 `name` 路径是否是**绝对路径**？
2. 路径指向的文件是否存在？确认文件在 `scratch-plugin/src/index.ts`。
3. 运行 `pwd` 确认你确实在仓库根目录。

> **关于 Web UI**：这个命令还会启动一个 Web 界面（默认在 `http://127.0.0.1:3080`），但本章不关心 UI——我们只需要确认插件被加载了。

看到 `[hello-plugin] plugin loaded!` 的那一刻，你的第一个 Harness 插件就成功运行了。用 `Ctrl+C` 停止进程。

### 这一节你学到了什么

- 插件是一个导出 `name` 和 `apply` 的 TypeScript 模块
- `ctx` 是插件的运行上下文，所有能力通过它暴露
- 通过 `--patch ./scratch-plugin/cordis.yml` 加载本地开发的插件
- patch 文件中的插件路径必须是**绝对路径**

## 2.5 插件的三种写法

上一节展示了最简单的函数形式。Cordis 支持三种插件写法，适用于不同场景。

### 函数形式（推荐：简单工具、无状态插件）

这就是你刚才写的模式。适用于大多数场景：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'simple-logger'

export function apply(ctx: Context) {
  // 函数体直接写插件逻辑
  ctx.on('ready', () => {
    console.log('simple-logger is ready')
  })
}
```

**什么场景用：** 记录日志、注册事件监听、注册工具——不需要维护内部状态时，函数形式最简洁。

### 对象形式（推荐：需要配置的插件）

当插件需要声明配置项或作为 `default export` 使用时，用对象形式：

```ts
import type { Context } from '@deepseek-ai/cordis'

// 默认导出整个对象，而不是分别导出 name 和 apply
export default {
  // name 和 apply 现在是对象的字段
  name: 'configurable-greeter',

  // inject 声明该插件需要哪些服务。
  // 框架会确保这些服务就绪后才调用 apply。
  inject: ['tools'],

  // apply 是对象的普通方法
  apply(ctx: Context) {
    console.log(`configurable-greeter loaded with tools service`)
  },
}
```

**什么场景用：** 插件需要导出 `Config` 类型和 schema（第 4 章会讲）、需要声明 `inject` 依赖、或者你想用 `default export` 统一导出。对象形式更结构化，方便附加元数据。

### 类形式（推荐：对外提供服务的插件）

当插件需要向其他插件提供服务时，继承 `Service` 类：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

export default class MyService extends Service {
  // 静态 inject 声明这个服务依赖的工具
  static inject = ['tools']

  constructor(ctx: Context) {
    // super(ctx, '<服务名>') 注册一个名为 myService 的服务
    // 其他插件可以通过 ctx.myService 访问它
    super(ctx, 'myService')

    // 在构造函数中做同步初始化
    console.log('MyService constructed')
  }

  // 可以定义对外暴露的方法
  greet(name: string): string {
    return `Hello, ${name}!`
  }
}
```

**什么场景用：** 你的插件需要提供 API 给其他插件调用。比如一个缓存服务、一个配置管理中心、或者你封装了某个第三方 SDK。类形式让其他插件可以通过依赖注入来使用你的服务。

### 三种形式对比

| 形式 | 导出方式 | 适用场景 | 能否提供服务 |
|------|---------|---------|------------|
| 函数 | `export function apply` | 简单工具、日志、监听事件 | 否 |
| 对象 | `export default { ... }` | 需要配置、依赖注入 | 否 |
| 类 | `export default class extends Service` | 需要向其他插件暴露 API | 是 |

### 这一节你学到了什么

- 函数形式最简单，适合大部分场景
- 对象形式结构化，适合需要配置的插件
- 类形式通过 `extends Service` 对外提供服务
- 三种形式的核心都是 `apply` 函数——框架最终调用的都是它

## 2.6 插件加载机制

现在你知道了怎么写插件和怎么加载它，但背后发生了什么？这一节解释加载机制的关键概念。

### cordis.yml 的结构

`cordis.yml`（或 patch 文件）本质上是一个插件配置项的数组。每个配置项告诉框架"加载哪个插件、给什么配置"。最基本的结构：

```yaml
- insert:
    - id: hello          # 插件实例的唯一标识
      name: '路径或包名'  # 指向插件模块
```

- **`id`**：插件实例的 ID，在同一份配置中必须唯一。用于在日志中标识具体实例，也用于后续配置层按 ID 覆盖配置。
- **`name`**：指向插件模块的路径（绝对路径）或 npm 包名（如 `@deepseek-ai/dsh-base`）。

### --patch 是什么

`--patch` 是 CLI 提供的一个机制，让你能在不修改原有配置的情况下，**叠加**一层新配置。`--patch ./scratch-plugin/cordis.yml` 的语义是：

1. 加载默认配置（比如 `@deepseek-ai/dsh-base` 提供的 base 配置）
2. 把你的 patch 文件的内容**叠加**上去
3. 如果同一 `id` 的插件在两层中都出现，后一层覆盖前一层

这很像 Git 的 patch——你改动一小部分，而不是重写整个配置。这让本地开发非常方便。

### name 和 id 的区别

这是一个容易混淆的点：

- **`name`** 是插件模块的标识，指向代码文件或 npm 包。它告诉框架"去哪里找代码"。
- **`id`** 是插件实例的标识，在运行时唯一标识这个插件实例。它告诉框架"这是哪个插件实例"。

多个不同的 `id` 可以指向同一个 `name`（即同一份代码可以加载多次），但同一个 `id` 在同一生效配置中不能出现两次。

### 多个插件的加载顺序

在 `cordis.yml` 中列出的插件，**不是你排在前它就先加载**。实际加载顺序由**依赖关系**决定：

- 插件 A 声明 `inject: ['tools']`，插件 B 提供 `tools` 服务
- A 会等 B 就绪后才开始加载
- 如果两个插件没有相互依赖，它们**并发加载**

如果想控制顺序，应该通过 `inject` 声明依赖，而不是靠 YAML 中的排列位置。

### 如何禁用插件

如果想临时关掉某个插件，不需要删除配置行，只需要加一个标记：

```yaml
- insert:
    - id: hello
      name: '/path/to/scratch-plugin/src/index.ts'
      disabled: true   # 框架会跳过这个插件的加载
```

`disabled: true` 的插件完全不会被加载，就像它的配置行不存在一样。

### 这一节你学到了什么

- `cordis.yml` 是插件配置的数组，`--patch` 叠加配置层
- `name` 是代码位置，`id` 是实例标识
- 插件按依赖关系排序，不是按 YAML 中的顺序
- 用 `disabled: true` 临时禁用插件，无需删除配置

## 2.7 自动清理机制

写插件时你经常需要管理资源：定时器、文件句柄、网络连接……如果插件被卸载了，这些资源必须被回收。Cordis 提供了自动清理机制。

### ctx.effect()：注册清理函数

当你通过 `ctx` 注册任何东西（事件监听、工具等），框架会自动追踪并在卸载时清理。对于框架不认识的自定义资源，用 `ctx.effect()` 来注册清理逻辑：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'heartbeat-plugin'

export function apply(ctx: Context) {
  // ctx.effect() 接受一个工厂函数：
  // - 工厂函数在插件加载时立即执行
  // - 工厂函数返回一个"清理函数"（disposer）
  // - 清理函数在插件卸载时被调用
  ctx.effect(() => {
    // 1. 在加载阶段创建定时器
    const timer = setInterval(() => {
      console.log('heartbeat')
    }, 5000)

    // 2. 返回清理函数——框架会记住它
    //    当插件卸载时（无论什么原因），框架会调用这个函数
    return () => {
      clearInterval(timer)
      console.log('heartbeat cleaned up')
    }
  })
}
```

**执行顺序：**

加载时打印 → `setInterval` 开始运行
卸载时 → `clearInterval(timer)` → 打印 "heartbeat cleaned up"

### 插件的卸载场景

插件可能在以下几种情况下被卸载：

1. **配置变更**：修改 `cordis.yml` 中某插件的配置后，框架自动卸载旧实例、加载新实例。
2. **HMR（热模块替换）**：启用 HMR 插件后，修改源文件会自动触发重新加载——先卸载旧版本、再加载新版本。
3. **手动卸载**：通过 `ctx.plugin()` 动态加载的插件可以用返回的 fiber 对象手动卸载。
4. **依赖服务消失**：如果插件依赖的服务（如 `tools`）被替换或移除，框架自动卸载该插件。
5. **进程退出**：应用关闭时，所有插件的清理函数依次执行。

重点是：**你不需要手动管理清理**。只要资源是通过 `ctx.effect()` 注册的，或者通过 `ctx.on()`、`ctx.plugin()` 等框架 API 创建的，它们在插件卸载时都会被自动回收。

### 自动清理的完整列表

以下操作都是"自带清理"的，不需要额外写 cleanup：

- `ctx.on(event, handler)` — 事件监听，卸载时自动移除
- `ctx.plugin(childPlugin)` — 子插件，随父插件一同卸载
- `ctx.tools.register(tool)` — 工具注册，卸载时自动撤销
- `ctx.llm.registerAdapter(...)` — LLM 适配器注册，卸载时自动撤销
- `ctx.effect(() => cleanup)` — 自定义资源，你提供清理函数

### 联系第 3 章

自动清理是 Cordis 框架提供的能力。第 3 章会深入 Cordis 的生命周期管理，包括 Fiber 状态机（`PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED`）以及为什么清理是按注册顺序逆序执行的。

### 这一节你学到了什么

- 通过 `ctx` 注册的资源会被框架自动追踪和清理
- 自定义资源用 `ctx.effect()` 注册清理函数
- 插件卸载发生在多种场景：配置变更、HMR、手动卸载、依赖消失
- 你不需要手动 removeListener 或 clearInterval——框架替你做了
