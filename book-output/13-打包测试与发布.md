## 11.1 打包插件为组合包

### 组合包（Bundle）vs 普通插件

在 DSH 生态中，插件和在架构层面是两个不同的概念。你写的一个 `.ts` 文件定义了插件（plugin），但要让 DSH 的 Loader 在启动时加载它，需要把它打包成**组合包（bundle）**——一个附带配置层的 npm 包。一个包可以有多个插件，一个组包也可以声明一个 patch 文件来插入这些插启行。

简单说：普通 npm 包只提供代码；组合包在代码之外还贡献了一层 Cordis 配置。

### package.json 的 dsh.bundle 声明

在组包目录下创建标准的 npm 包结构，并在 `package.json` 中声明 `dsh.bundle`：

```
hello-plugin/
├── package.json       # 声明 dsh.bundle
├── cordis.patch.yml   # 组合包贡献的配置层
└── index.js           # 插件模块
```

`package.json`

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

关键字段是 `dsh.bundle.patch`，指向组合包要应用的 patch 文件。

### cordis.patch.yml 的结构

patch 文件是你之前通过 `--patch` 参数加载的 YAML 数组。唯一的区别是插件行不再引用相对源码路径，而是按包名引用：

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin
```

组合包也可以覆盖已有行的配置。例如，`dsh-web-app` 包就是这样覆盖 `dsh-base` 中某行的。注意 patch 替换的是整行 config，不是深度合并——你需要重述该行的每一个键。

### 安装到 Profile：dsh plugin add

在包含 `hello-plugin` 的目录下执行：

```sh
dsh plugin --profile demo add ./hello-plugin
```

这条命令做了三件事：

1. 如果 profile `demo` 不存在，初始化它（`@deepseek-ai/dsh-base` 作为第一个组包）；
2. pnpm 将 `hello-plugin` 链接进 profile；
3. 检测到 `dsh.bundle` 声明后，把包名追加进 `dsh.profile.bundles` 列表。

验证安装结果：

```sh
dsh --profile demo --dump-config   # 查看组合层
dsh --profile demo                  # 正常启动
```

卸载同样简单：

```sh
dsh plugin --profile demo remove dsh-hello-plugin
```

不加 `dsh.bundle` 声明的包也可以安装，只会被当作普通依赖——`dsh plugin` 打印警告但不激活任何层。

### 加载顺序和层叠

生效配置在空根之上按以下顺序逐层叠加：

1. profile 的 `dsh.profile.bundles` 所列组包的 patch，按列表顺序——先是 `@deepseek-ai/dsh-base`，然后按安装顺序排列各用户组包。
2. profile 自己的 `cordis.patch.yml`（用户自己的 patch）。
3. Home 级 `$DSH_HOME/cordis.patch.yml`（各 profile 共享的机器本地偏好）。
4. 每个 `--patch <path>` overlay，按 argv 顺序。

后应用的层按行胜出，整行替换，不做深度合并。这意味着你的 patch 可以按 `id` 覆盖前面各层的行，但必须重述整行。也意味着用户可以在 profile 的 `cordis.patch.yml` 中覆盖你的行，而无修改你的包——这是设计意图：插件作者给出合理的默认值，让用户通过自己的 patch 层按需调整。

## 11.2 Profile 与配置管理

### 什么是 Profile

Profile 是位于 `$DSH_HOME/profiles/<name>` 下、描述一套可启动组合的目录。它是 DSH 的配置单元——不同的 profile 可以持有不同的组合包集合和参数，互不干扰。

### Profile 的目录结构

```
$DSH_HOME/profiles/demo/
├── package.json         # 包含 dsh.profile 和 pnpm 管理的依赖
├── cordis.patch.yml     # 用户自己的 patch 层
└── pnpm-lock.yaml       # 依赖锁定文件
```

Profile manifest 从不需要手写——`dsh plugin` 命令负责创建和维护它。它的 `dsh.profile.bundles` 数组是有序的组包列表。

### 配置的层叠顺序

见 11.1 节的加载顺序。理解层叠是为了回答"如果两个包都修改了同一个插件的配置，谁生效？"——后加载的胜出。

### 用户 patch vs 默认配置

这条规则决定了插件作者的策略：

- **你的 patch 应该提供合理的默认值。** 用户大概率会保留的值放在这里。
- **用户的 profile cordis.patch.yml 是定制层。** 他们覆盖你是预期行为。
- **不要在你的 patch 里写死用户很可能要改的值。** 把这类值交给 schema 和运行时配置。

### 多环境配置管理

你可以为不同环境创建多个 profile：

```sh
dsh plugin --profile dev add ./my-plugin
dsh plugin --profile staging add ./my-plugin
dsh plugin --profile prod add ./my-plugin
```

每个 profile 拥有独立的组包集和 patch 层。启动时用 `--profile` 切换：

```sh
dsh --profile dev
dsh --profile staging
dsh --profile prod
```

结合环境变量（如 `NODE_ENV`），这是 DSH 原生的多环境配置方案，不需额外工具。

## 11.3 测试策略

测试是插件质量的最后一道防线。本节从 DSH 仓库自身积累的经验出发，介绍测试的分层方法和一个重要的教训。

### 测试分层：单元测试 → 集成测试 → e2e

- **单元测试**：覆盖工具 execute 的逻辑、边界条件、错误路径和并发竞态。与代码放在一起，在 `tests/` 目录下。
- **集成测试**：测试插件加载和依赖注入是否正常。需要轻量 harness，模拟 Cordis 上下文。
- **E2e 测试**：通过真实的 Loader 和子进程启动 profile，只 mock 非确定性边界（模型适配器、网络等），断言模型可见的输出或持久状态。

### 单元测试：测试工具 execute 逻辑

工具插件的核心是 `execute` 函数。单元测试应该覆盖：

```typescript
import { describe, it, expect } from 'vitest'
import { myTool } from '../src/index.ts'

describe('myTool', () => {
  it('正常输入返回正确结果', async () => {
    const result = await myTool.execute({ input: 'hello' })
    expect(result.success).toBe(true)
    expect(result.data).toContain('hello')
  })

  it('空输入返回错误', async () => {
    const result = await myTool.execute({ input: '' })
    expect(result.success).toBe(false)
  })

  it('超大输入不崩溃', async () => {
    const large = 'x'.repeat(100000)
    const result = await myTool.execute({ input: large })
    expect(result.success).toBe(true)
  })
})
```

### 集成测试：测试插件加载和依赖注入

集成测试验证插件的 `inject` 声明和上下文装配是否正确：

```typescript
import { Context } from '@deepseek-ai/cordis'
import { describe, it, expect } from 'vitest'
import { name, inject, apply, Config } from '../src/index.ts'

describe('myPlugin loading', () => {
  it('inject 声明与 apply 内使用的服务一致', () => {
    // 防止 inject 声明和实际使用脱节
    expect(inject).toContain('logger')
    expect(inject).toContain('config')
  })

  it('插入和卸载不泄漏', async () => {
    const ctx = new Context()
    ctx.plugin({ name, inject, apply, Config })
    ctx.effect('dispose', () => { /* clean up */ })
    await ctx.dispose()
  })
})
```

### E2e 测试：真实 Loader 路径

这是整个测试体系中最关键的层级，也是最容易被忽视的。**手动构建 `ctx.plugin(...)` 的测试永远不够**。以子进程方式通过真实 Loader 启动 profile：

```typescript
import { describe, it, expect } from 'vitest'
import { execa } from 'execa'

describe('myPlugin e2e', () => {
  it('通过真实 Loader 加载不报错', async () => {
    // 使用构建后的 lib/ 启动真实子进程
    const proc = execa('node', ['lib/cli.js', '--profile', 'test'], {
      env: { ...process.env, NODE_ENV: 'test' }
    })
    await expect(proc).toResolve()
  })
})
```

### 快照测试

对生成提示词、工具列表等确定性的输出做快照测试。当模型 transcript 变化时用 record 模式更新，但每次 diff 都必须人工审查。

### 测试真实入口路径——从 ACP Postmortem 学到的教训

DSH 仓库著名的 **Postmortem 0001** 深刻揭示了假性安全的危害。

事故复盘还原：ACP 服务器在真实编辑器连接的瞬间崩溃。`session/new` 返回 `Internal error`，`session/load` 返回同样的错误。然而测试套件——178 个绿色单元测试，100% 行覆盖率——全部通过。两个独立 bug 隐藏在同一个错误字符串背后。

Bug 1 的根因是：ACP 插件的 `index.ts` 中有一行似乎无害的 `export default apply`。Cordis Loader 的 `unwrapExports` 函数存在默认导出时用 `exports.default ?? exports` 取值，结果取到的是**裸 `apply` 函数**。函数本身没有 `inject` 属性——这些属性是模块命名空间的同级导出，`unwrapExports` 选择了 `.default` 就把整个命名空间丢弃了。Loader 基于空的 `inject` 构建 fiber，`ctx.agents` 抛出 `cannot get property "agents" without inject`。

Bug 2 涉及 Cordis 可追踪代理的 shadow 机制：服务访问的 fiber 遍历只向祖先方向进行，而目标服务在一个兄弟 fiber 上。手动构建的测试从顶层读取服务——`ctx.fiber.runtime` 为 `null` 时走的是直接全局 store 查找——刚好绕过了这个拓扑陷阱。

**为什么测试没有捕获？** 所有测试都通过 `ctx.plugin(...)` 手动挂载插件。这条路径从不调用 Loader 的 `unwrapExports`，也从不形成真实的 fiber 树拓扑。测试在模拟世界中全绿，真实生产路径却全线瘫痪。

**教训一：** 至少一个测试必须通过真实 Loader 驱动插件的加载路径。手动构建的 `ctx.plugin` 不足以验证了插件的加载方式。

**教训二：** 行覆盖率不等于行为覆盖率。100% 的行覆盖只证明每行代码被执行过，不证明它们在交付路径上按预期工作。

**教训三：** 命名空间插件与 `export default` 在 Cordis Loader 下互斥。选命名空间形式（具名导出 `name`/`inject`/`Config`/`apply`），不要写 `export default`。

**教训四：** 对于插件机会性读取但未在 `static inject` 中声明的服务，使用 `ctx.get(name)` 而非 `ctx.<name>`。属性代理通过仅向祖先方向的 fiber 遍历解析，`ctx.get()` 是拓扑无关的查找。

把这些规则写进你的测试策略：每个面向用户的包至少配一个真实 Loader 的无密钥 e2e 测试。

## 11.4 代码审查

DSH 仓库使用 `dsh-code-review` skill 维护标准化的审查流程。本节提炼其中要点，供插件作者作为自检清单。

### 审查清单

提交前逐项检查：

- [ ] 插件是否使用命名空间导出（具名 `name`/`inject`/`Config`/`apply`）而非 `export default`？
- [ ] `inject` 声明是否与实际使用的服务完全一致？既不要多列（引入不必要的依赖），也不要少列（导致运行时崩溃）。
- [ ] 配置 schema 是否有合理的默认值？默认值是否在大多数场景下都安全工作？
- [ ] 所有用户输入是否有边界处理？包括空值、超长值、特殊字符、负数等？
- [ ] 错误路径是否有测试覆盖？`execute` 报错时是否返回了有意义的错误信息？
- [ ] 是否包含至少一个真实 Loader 路径的 e2e 测试？
- [ ] 是否有不必要的 `export default`？
- [ ] package.json 的 `files` 字段是否精确地只包含发布所需文件？

### 常见问题

下面是审查中反复出现的反模式，列出具体例子：

**硬编码。** 插件的 API 端点、超时值、路径等应该通过配置或 schema 暴露，而非写在源码里：

```typescript
// 不推荐
const API_URL = 'https://api.example.com/v1'

// 推荐
export const Config = Schema.object({
  apiUrl: Schema.string().default('https://api.example.com/v1'),
  timeout: Schema.number().default(5000),
})
```

**缺失边界处理。** 工具函数对空输入、超大输入、并发调用等未做保护：

```typescript
// 不推荐
async function searchFiles(query: string) {
  return fs.readdir(query) // query 为 '' 时读当前目录，可能不是预期行为
}

// 推荐
async function searchFiles(query: string) {
  if (!query.trim()) throw new Error('query cannot be empty')
  // 安全检查——防止路径遍历攻击
  if (query.includes('..')) throw new Error('invalid query')
  return fs.readdir(query)
}
```

**不合理的默认值。** 给某个配置项设置的默认值可能在工作不正常的同时静默吞掉错误。例如，一个文件搜索工具把 `maxResults` 的默认值设为 `Infinity`——这在被大量文件触发时可能导致进程内存溢出。

**缺少 `inject` vs 实际使用的一致性检查。** 这是 Postmortem 0001 类问题的变体：服务声明了但不使用（冗余），或者使用了但不声明（运行时崩溃）。代码审查时应对照阅读 `inject` 数组和 `apply` 函数体。

### 堆叠 PR 的处理

当多个 PR 形成依赖链（`A ← B ← C`）时，审查反馈的修复遵循一条铁律：**修复落在引入问题的那个 PR 上，然后沿堆叠向上传播。** 不要在 `C` 上修复 `A` 引入的 bug，否则合并后 `A` 会带着未修复的代码进入主线。

每次修复保持独立 commit，评审后可以用 rebase 改写历史（受 lease 保护的 force push），但不要 amend 已评审的 commit。

### 响应审查反馈

面对评审意见的实践建议：

1. **先验证后反驳。** 评审者指出了正确的症状，但仍可能误诊原因。对照代码验证每一条评论，确信后再行动。
2. **每条反馈都要明确回应。** "已修复"或"已确认，但此处不作修改，原因如下"——留空不回的线程会让评审者不确定你是否已处理。
3. **堆叠链中的修复需要传播验证。** 在 `B` 上修复后，合并到 `C`，确保 `C` 的 CI 也通过。
4. **信任但验证 subagent 的修复。** 如果委托 subagent 处理，实际代码上重新运行门禁。对回归守卫，证明它在未修复的代码上失败——两边都通过的守卫守不住任何东西。

## 11.5 发布

插件通过代码审查、测试通过后，就可以发布了。

### 发布到 npm

这是最推荐的发布方式。先确认 `package.json` 中的 `files` 字段只包含需要发布的文件：

```json
{
  "files": ["lib/", "cordis.patch.yml", "README.md"]
}
```

然后发布：

```sh
pnpm publish
```

发布后，用户可以通过以下命令安装：

```sh
dsh plugin --profile demo add dsh-hello-plugin
```

### 发布 tarball

如果不方便发布到 npm，可以用 `pnpm pack` 打包为 tarball：

```sh
pnpm pack
```

生成 `dsh-hello-plugin-0.1.0.tgz`，用户直接安装：

```sh
dsh plugin --profile demo add ./dsh-hello-plugin-0.1.0.tgz
```

tarball 是预构建产物，用户不需要构建工具链。

### 从 GitHub 安装

从 git 托管直接安装：

```sh
dsh plugin --profile demo add github:you/hello-plugin
```

**注意：** git 安装拉取的是源码，不是构建产物。没有任何环节运行你的 `build` 脚本。如果插件是用 TypeScript 编写的，到手时没有 `lib/` 输出，加载会失败。

解决方案是提供 `prepare` 脚本——pnpm 在 git 安装后运行它，从源码构建发布入口。`prepare` 必须自包含，不能假设 monorepo checkout 等仅开发环境才有的上下文。参考 `turtle-ui` 的 setup：`prepare` 运行专用转译配置，直接转译 `src/`，不依赖项目引用或类型检查。

用户还需要授权构建。pnpm 10+ 在得到显式允许之前拒绝运行 git 依赖的 `prepare`。首次安装失败后，按 `dsh` 提示把包键添加到 profile 的 `pnpm-workspace.yaml`：

```yaml
allowBuilds:
  dsh-hello-plugin: true
```

然后重新执行 `add`。请把这看作是允许该包的代码在安装时于你的机器上执行。只对可信任的包授权，建议锁定 commit（`github:you/hello-plugin#<sha>`），让后续推送无法悄悄改变运行内容。

### CI 配置建议

在插件仓库中配置 CI，确保每次 PR 和合并都自动运行以下检查：

```yaml
steps:
  - run: pnpm install
  - run: pnpm run lint
  - run: pnpm run typecheck
  - run: pnpm run test:coverage
  - run: pnpm run build
  - run: pnpm run test:e2e   # 无密钥时可跳过
```

特别强调构建后跑一次 e2e 测试——只有构建后的产物才是用户实际运行的东西，tsx 或 vitest 跑的测试可能掩盖构建相关的问题。

## 11.6 双语文档规范（简要）

DSH 仓库要求范围内的每篇文档同时维护英文和中文版本。如果你的插件面向中英文用户，建议遵循这套规范。

### 文件结构

一篇 wiki 文档对应三个文件，放在同一目录：

```
foo.md          # 英文
foo.zh.md       # 中文
foo.i18n.yaml   # 一致性记录
```

`foo.i18n.yaml` 记录两侧文件在上次确认"说同样的话"时的 Git blob hash：

```yaml
foo.md: 3f786850e387550fdab836ed7e6dc881de23001b
foo.zh.md: 89e6c98d92887913cadf06b2adb97f26cde4849b
```

### 配对门禁

`verify-translation-pairing` 机械地强制执行一致性：

1. 范围内的每篇文档都有完整的三文件配对；
2. 任一测的当前 blob hash 等于记录值——改了任一侧没重新确认配对就变红；
3. 中文文件在 H1 后必须以 `[English](foo.md) | 中文` 链回英文；
4. 标题深度与顺序、代码块、表格、列表结构——在配对两侧一一对应。

_PR 修改了任一侧，必须在同一个 PR 内同步更新另一侧并重新记录 hash。留下失步配对的 PR 会在 CI 变红。_

### 翻译原则

- **两语言同权。** 既可以是先写英文再译中文，也可以先写中文再译英文。
- **术语统一。** 使用 `terminology.md` 中维护的术语表。
- **AI 辅助后必须人工审校。** 门禁只能检查 hash 和结构一致性，无法判断两侧是否说同样的话。

## 11.7 本章小结

从插件代码到可安装的交付物，本章走完了打包→测试→审查→发布的全流程。关键要点：

- **组合包 vs 普通包**：组合包通过 `dsh.bundle` 声明贡献配置层，通过 `dsh plugin add` 安装进 profile。
- **Profile 是配置单元**：多 profile 实现多环境管理，层叠顺序决定配置优先级。
- **测试要分层，但关键在 e2e**：单元测试加上集成测试还不够——至少一个真实 Loader 路径的 e2e 测试是必需的。Postmortem 0001 的教训证明了手动构件插件的测试无法验证插件的真实加载路径。
- **代码审查要有清单**：检查命名导出、inject 一致性、边界处理、默认值合理性。
- **发布方式三选一**：npm 发布最通用，tarball 最轻量，git 安装需要 `prepare` 脚本和构建授权。
- **双语文档是硬性要求**：三文件配对，CI 门禁强制执行一致性。

第 12 章开始进入"进阶调试"篇，涵盖日志、性能分析和故障排查。
