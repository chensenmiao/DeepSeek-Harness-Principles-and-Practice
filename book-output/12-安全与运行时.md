## 10.1 沙箱机制

让一个 AI agent 直接执行代码，本质上等于把一个陌生人请进你的厨房，对他说："随便用，别客气。"如果没有明确的边界——什么炉灶能用、什么橱柜不能碰、调料可以动但菜刀不行——一次"善意"的尝试完全可能变成一场灾难。

### 为什么需要沙箱

AI 生成并执行的代码可能做很多事情：读文件、写文件、启动子进程、访问网络。其中许多操作本身并没有恶意意图，甚至就是用户期望的功能。但问题的关键在于，AI 不具备人类的判断力来判断一个操作的"副作用范围"。它可能因为你的一句"帮我清理硬盘"，就把整个项目目录删干净。

Harness 的沙箱机制解决的核心问题不是"AI 是否会作恶"（那是安全对齐的范畴），而是"一个不可信进程在文件系统上的效果边界在哪里"。沙箱不回答"能不能运行"，只回答"能碰到哪里"。

### 三种沙箱模式

Harness 定义了三种文件效果策略，由 `SandboxMode` 类型表示：

```ts
type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'
```

可以把它们理解成厨房的三个权限等级：

- **`read-only`**：你只能看菜谱，不能碰任何食材。进程可以读取文件系统的内容，但不能创建、修改或删除任何文件。唯一特例是 POSIX 系统上 shell 所需的 `/dev/null`——那是呼吸管，不是抹布。

- **`workspace-write`**：你可以在自己的料理台上操作。进程可以在工作区根目录（workspace root）以及后端指定的临时区域内写入文件。这是日常开发使用中最常见的模式——agent 可以创建和修改项目文件，但不能碰系统目录或其他项目。

- **`danger-full-access`**：不设边界，厨房归你。绕过所有隔离，进程以原始权限运行。仅适用于用户明确授权的高风险场景（例如安装系统级依赖）。

值得注意的是，`danger-full-access` 不会发送给沙箱提供方——当策略解析为该模式时，消费方直接 spawn 原始 argv，不经过 `ctx.sandbox`。

### 不同系统的实现

沙箱不是魔法，它在不同操作系统上依赖不同的内核机制：

- **Linux（bwrap / Landlock）**：bubblewrap（bwrap）是用户命名空间的经典方案，通过创建隔离的 mount namespace 限制文件系统视图。Landlock 是较新的 LSM（Linux Security Module），提供更细粒度的文件权限控制。Landlock 的旧 ABI 版本可能存在"部分强制执行"的问题——即某些文件效果无法被管控，消费方需要感知这一区别。

- **macOS（Seatbelt）**：Apple 的 Seatbelt 框架通过 Sandbox Profile 限制进程能力。Seatbelt 对文件系统写入的管控效果较好，但对进程间通信的边界边界不如 Landlock 明确。

- **Windows（ACL）**：Windows 通过受限令牌和访问控制列表（ACL）实现沙箱。Windows ACL runner 的局限性在于 Everyone 组和硬链接边界可能导致权限泄漏，因此它的强制执行完整性报告为 `partial`。

### 强制执行完整性

后端在返回 `ConfinedArgv` 时会如实报告 `enforcement`：

```ts
type SandboxEnforcement = 'full' | 'partial'
```

- **`full`**：后端覆盖了该模式下承诺的所有文件效果。你可以信任它。
- **`partial`**：当前后端或内核 ABI 只能覆盖部分边界。需要绝对隔离的消费方应当拒绝执行或向上暴露这一信息。

这个设计遵循一个重要原则：**永远不要假装安全比实际更严格。** 给一个实际上只锁了前门的笼子挂上"绝对安全"的牌子，比不挂牌子更危险。

### fail-closed 原则

当沙箱不可用时，系统必须拒绝执行，而不是静默降级。`ctx.sandbox.confine(argv, policy)` 在没有可用后端时抛出 `SandboxUnavailableError`（错误码 `SANDBOX_UNAVAILABLE`）。对于受限策略，静默的无隔离透传永远不合法。

```ts
// 消费方安全地调用沙箱
try {
  const confined = ctx.sandbox.confine(argv, policy)
  spawn(confined.argv)
} catch (e) {
  if (e.code === 'SANDBOX_UNAVAILABLE') {
    // 沙箱不可用 → 拒绝执行，不静默降级
    return { isError: true, content: '沙箱不可用，已阻止命令执行' }
  }
  throw e
}
```

## 10.2 沙箱执行策略

### 逐调用策略解析

沙箱策略不是一次性设置后就固定的。它在每次能力调用时重新解析，这带来了极大的灵活性。

```ts
interface SandboxExecutionPolicy {
  mode: SandboxMode
  workspaceRoot: string
  sessionId?: SessionId
}
```

策略解析的优先级链为：

1. **显式批准的覆盖模式**（优先级最高）——例如用户明确同意了一次提权操作
2. **会话中最后一次 `sandbox/mode` 事件**——用户或插件在会话过程中切换了模式
3. **部署默认配置**——系统管理员设定的全局默认值

这种逐调用设计解决了并发场景下的核心矛盾：同一个提供方（例如 bash shell）可以被两个不同的消费方在同一时刻以不同的策略调用。一个 agent 在 `read-only` 下运行 bash，而另一个子 agent 需要向自己的状态目录写入数据——两者互不干扰。

```ts
// 消费方在每次执行前解析策略
const policy = ctx.sandboxPolicy.resolve({ session })
// policy.mode 可能为 'read-only'
// policy.workspaceRoot 指向会话的不可变 cwd
```

### ctx.sandbox 和 ctx.sandboxPolicy

这两个服务有不同的职责：

- **`ctx.sandbox`** —— `SandboxProvider`，抽象的进程沙箱服务。核心方法只有一个：`confine(argv, policy) → ConfinedArgv`。它负责把 argv 包装成受限版本。只有受限的调用才会到达它；`danger-full-access` 的策略根本不会传递给它。

- **`ctx.sandboxPolicy`** —— `SandboxPolicyService`，策略解析服务。它拥有部署默认模式、回退工作区根目录和运行时的策略解析逻辑。工具层在每次执行时调用 `resolve()` 获取策略。

```ts
// ctx.sandboxPolicy.resolve() 的签名
resolve(request: SandboxPolicyRequest = {}): SandboxExecutionPolicy

// 支持显式模式覆盖（用于已批准的重试）
const escalatedPolicy = ctx.sandboxPolicy.resolve({
  session,
  mode: 'workspace-write' // 显式覆盖会话策略
})
```

### 工作区根目录管理

工作区根目录（workspace root）由调用会话的不可变 cwd 决定。系统会先按文件系统语义规范化路径（解析符号链接），再做词法规范化。这意味着如果 cwd 包含 `symlink/..` 这样的路径段，规范化后会得到进程实际运行的目录，而非文本层面的路径。

对于没有 agent 的调用（例如部署配置），系统使用配置中设定的回退根目录。

### 已批准重试的特殊处理

当用户批准了一次权限提升请求后，对应的重试调用会携带显式的模式覆盖。这个覆盖在优先级链中最高，因此即使会话策略是 `read-only`，被批准的 `workspace-write` 操作也能正常执行。更重要的是，这个覆盖是**逐调用**的——它不会改变会话的持久化策略，下一次调用仍然以原始策略执行。

## 10.3 权限系统与审批

### 权限预设

权限预设把两个独立的控制旋钮——沙箱模式（`sandbox/mode`）和审批策略（`approval/policy`）——捆绑成一个具名预设。

```ts
interface PresetSpec {
  sandbox: SandboxMode
  approval: ApprovalPolicy
  name?: string
  description?: string
}
```

系统默认提供两个预设：

| 预设名 | 沙箱模式 | 审批策略 | 适用场景 |
|---|---|---|---|
| `workspace-write` | workspace-write | ask | 日常开发，需要询问用户 |
| `danger-full-access` | danger-full-access | never | 无限制，不询问 |

预设表是可扩展的——部署可以添加自己的预设（例如一个"只读审计"预设：`read-only` + `never`）。

预设的 `current()` 方法会从旋钮的实际生效值派生当前预设，而不是仅仅查看预设事件本身。如果用户手动调整了沙箱模式或审批策略，使得当前状态不再匹配任何预设，系统会返回 `custom`——表示当前是"自定义"组合，不等于任何预设。

### 预设的种类和切换

用户可以通过客户端的选择器切换预设。切换时，`ctx.permissionPresets.set(session, name)` 会记录一条 `permission/preset` 日志事件，然后通过各自旋钮的 setter 写入新的沙箱模式和审批策略。只有当某个旋钮的生效值确实发生变化时，才会实际写入。

重新选择当前已经生效的预设不会产生任何操作——这是幂等性保证。

### 用户审批流程

当 agent 需要执行一个需要用户确认的操作时，它通过 `ctx.approval.request()` 发起审批请求。

```ts
type ApprovalPolicy = 'ask' | 'never'
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
```

- **`ask`**：询问用户。通过组合的应答者链分发请求。如果没有任何应答者能处理，返回 `unavailable`。
- **`never`**：永不询问，确定性地返回 `rejected`。这是无头模式（CI、无人值守运行）的唯一合法选择。

`never` 策略在服务内部、分发之前就强制执行——即使后来以 `prepend` 注册的应答者也无法绕过它。这是安全底线，不是配置建议。

### 在插件中请求用户审批

插件开发者可以通过监听 `approval/request` 事件来提供自定义的审批逻辑：

```ts
// 注册一个应答者
ctx.on('approval/request', async (req, next) => {
  if (req.toolName === 'bash') {
    // 对于 bash 调用，显示高危操作警告
    const confirmed = await showDialog({
      message: `Agent 请求执行 bash 命令，是否允许？`,
      reason: req.reason,
    })
    return confirmed ? 'allowed-once' : 'rejected'
  }
  // 其他工具委托给下一个应答者
  return next()
})
```

应答者通过返回结果来"认领"请求，或调用 `next()` 委托。第一个应答占据唯一的决策槽位。返回值不是 `'allowed-once'` 时，调用方都会拒绝。

## 10.4 会话持久化

### Session Event 流

Harness 的会话是一个**仅追加日志**，类型化的 `SessionEvent` 是其唯一真源（Source of Truth）。所有对话历史、工具调用、模型输出都记录在此。LLM 的消息历史是从日志**派生**的，而非单独存储。回放即从同一组事件重新派生。

```ts
interface SessionEventMap {
  'turn/start': { turn: number }
  'turn/end': { turn: number; reason: TurnEndReason }
  'step/start': { turn: number; step: number }
  'step/end': { turn: number; step: number }
  'user/message': UserMessage
  'assistant/chunk': { turn: number; step: number; chunk: StreamChunk }
  'assistant/message': { turn: number; step: number; message: AssistantMessage }
  'tool/call': { turn: number; step: number; callId: ToolCallId; name: string; arguments: string }
  'tool/result': { turn: number; step: number; message: ToolResultMessage }
  // ...
}
```

这个事件流通过 `SessionEventMap` 的类型合并使插件可以扩展自己的事件类型。例如压缩子系统添加了 `compaction/start`、`compaction/summary` 和 `compaction/end`。

### 持久化引擎：JSONL vs SQLite

Harness 提供两种持久化后端，都实现同一个 `SessionPersistence` 抽象：

- **JSONL 后端**：逐会话仅追加的逻辑 JSONL 日志。默认存储为带 checksum 的连续 Zstandard frame（压缩），也可配置为原始行。支持崩溃安全的原子写入和中断轮次的恢复。文件系统上的产物是独立文件，便于直接查看和调试。

- **SQLite 后端**：可选的 `node:sqlite` 实现。同一分片块中字段完全匹配的 delta 连续段存为有界物理行。查询效率更高，适合大规模部署。

两种后端的核心行为一致：
- `append()` 的 resolve 表示数据已持久（durability guaranteed）
- `load()` 总会返回一个平衡的日志（尾部被中断的轮次会被合成关闭）
- 崩溃恢复保留被中断轮次的所有事件，不截断

### 崩溃恢复

当一个在轮次中崩溃的会话重新加载时，持久化后端会发现一个已打开的 `turn/start` 却没有 `turn/end`。它不会截断日志——因为在长周期任务中，单个轮次可能包含大量已持久的事件。它改为用一个合成的 `turn/end { reason: { kind: 'interrupted' } }` 关闭这个遗留轮次，在不改变其前后事件的情况下配平被中断的执行。

```ts
// 崩溃恢复：保留事件，合成中断标记
// 日志原本是： [turn/start, step/start, tool/call, tool/result, ...]
// 恢复后变为：[turn/start, step/start, tool/call, tool/result, ...,
//              turn/end { reason: 'interrupted' }]
```

`interrupted` 是唯一的 `TurnEndReason`，不是由任何 loop 发出的——它只由崩溃恢复合成。

### 会话创建、恢复与 Fork

- **创建**：`ctx.sessions.create(id, { seed, meta })` 创建新会话。可选的 `seed` 用于回放或 fork 历史事件。
- **恢复**：`ctx.agents.resume({ resumeSessionId })` 将一个持久化的会话恢复为活跃 agent。
- **Fork**：`ctx.sessions.fork(source, boundary)` 接收一个活跃的 `Session`，选取到指定边界（含）为止的源事件，然后创建一个活跃的子会话，包含深克隆的种子事件和子会话元数据（`parentSession`、`seedLength` 及继承的 `cwd`）。

### 投影缓存优化

为了避免每次打开会话都全量回放事件日志，Harness 引入了会话投影缓存。每个领域插件注册一个纯函数单元：`init(state)` 初始化状态，`apply(state, event)` 折叠每个事件。框架驱动折叠过程，缓存折叠结果的状态快照。

```ts
interface ProjectionDefinition<K, S> {
  key: K
  init(header: SessionHeader): S
  apply(state: S, event: SessionEvent): S   // 纯函数：相同输入 → 相同输出
  stateVersion: number                       // 缓存失效版本号
}
```

当会话再次打开时，系统加载最新的缓存快照，然后只回放快照之后的新事件。这避免了每次加载都需要遍历全部历史。缓存以 `(sessionId, key, ver, seq, val)` 的形式持久化，版本号不匹配时自动失效。

## 10.5 压缩（Compaction）

### 为什么需要压缩

随着对话的持续，会话日志会不断增长。大量的工具调用结果（特别是 fetch、bash 等输出密集型工具）会消耗大量 token。压缩的核心思想是：**用一段摘要替换一段对话历史，在保留语义信息的同时大幅减少 token 消耗。**

### 自动压缩 vs 手动压缩

Harness 支持两种压缩触发方式：

- **自动压缩（pressure/context-overflow）**：在 `agent/pre-step` 事件中运行，先于请求推导。当上下文压力或模型报告溢出时，系统自动触发压缩。触发条件由策略配置决定（token 阈值、保留尾部大小等）。

- **手动压缩（compactNow）**：用户或插件主动请求压缩，即使会话未达压力阈值。

```ts
// 手动压缩
const result = await ctx.compaction.compactNow(agent, signal, sourceCommandId)
if (result) {
  console.log(`压缩完成：遮蔽了 ${result.shadowedSeqs.length} 个 surface 节点`)
}
```

### 工具结果剪枝

在压缩之前，可选的工具结果剪枝服务会截断过大的工具输出。它保留输出的头部和尾部，移除中间部分。剪枝是确定性的——相同的输入产生相同的输出——因此回放可以精确重建。

```ts
interface PrunedEntry {
  originalSeq: number          // 被替换的原始事件 seq
  replacementSeq: number       // 新追加的裁剪后事件 seq
  charsBefore: number          // 原始文本长度（Unicode code point）
  charsAfter: number           // 替换后文本长度
}
```

### 压缩对模型的影响

压缩对模型来说是透明的。压缩后的摘要通过 `user/message` 事件携带 `surfaceOp: { op: 'replace', start, end }` 替换被遮蔽的 surface 节点。模型看到的是替换后的消息历史，不知道背后发生了压缩。

压缩通过 `compaction/start`、`compaction/summary`、`compaction/end` 三个日志事件记录整个过程。如果压缩中途崩溃，日志中会留下一个只有 `compaction/start` 而无 `compaction/end` 的记录——崩溃恢复可以检测并处理这种遗留锁。

## 10.6 内容溢出（Spill）

### 为什么需要 Spill

一个 `web_fetch` 可能返回几 MB 的 HTML，一个 `bash` 命令可能输出数万行日志。如果这些超大内容全部内联到会话日志中：

1. 会话日志急剧膨胀，影响持久化和加载性能
2. 每次模型调用都要传输这些大内容，消耗大量 token
3. 可能超出模型上下文窗口的限制

Spill 机制解决这个问题：**超大内容自动溢出到独立文件，会话日志中只保留定位符和检索指引。**

### Spill 机制

当工具执行完毕，Spill 策略（`dsh-spill-policy`）在 `tools/post-execute` 中检查输出大小。如果超过 `maxInlineBytes` 阈值，纯文本结果被替换为：

1. 首尾预览（保留内容的前若干字符和后若干字符）
2. 一个 `SpillLocator`——模型可以使用的定位符

```ts
interface SaveTextSpill {
  owner: SpillOwner          // 存储命名空间（基于 sessionId）
  source: SpillSource        // 产生内容的工具和调用
  suggestedName: string      // 建议文件名（仅命名提示，非路径）
  content: string            // 完整文本内容
}
```

本地后端将内容写入 `<root>/session-<hash>/<random>-<safeName>` 路径。关键的安全措施：

- 根目录权限为 0700（仅所有者可访问）
- 使用 `sha256(sessionId)` 避免会话间的路径预测
- 以独占且仅所有者可访问的方式写入（`open(path, 'wx', 0o600)`），防止符号链接重定向攻击

### 模型可见性控制

Spill 文件的内容对模型并不是完全不可见的——模型可以通过 `read` 或 `grep` 工具读取 spill 文件。但关键在于：

- 模型**按需**读取，而非被动接收所有内容
- 首尾预览让模型能够判断是否需要读取完整内容
- 这类似于人类的工作方式：先看摘要，再决定是否展开详情

### 配置 Spill 策略

```ts
// 在插件配置中调整 Spill 阈值
{
  spill: {
    maxInlineBytes: 4096,     // 超过 4KB 的内容触发 Spill
  }
}
```

Spill 是尽力而为的操作：如果保存失败（权限不足、磁盘空间耗尽），系统会保留原始内联结果，不会把一次成功的工具执行标记为失败。

## 10.7 防御性编程原则

本节总结 Harness 项目从实际缺陷中提炼出的防御性编程规则。每条规则都对应一种已经在生产环境中或发布前被发现的缺陷类别。

### 正交结果独立报告

一个结果可以同时具有多种性质：进程可能已经超时，却仍以退出码 0 结束（因为它捕获了终止信号）。每个独立事实都应单独上报，切勿把一个标志的上报嵌套在另一个标志的分支中。

```ts
// 正确：正交报告
return { exitCode: 0, timedOut: true, signal: 'SIGTERM' }

// 错误：嵌套在 exitCode 分支中上报 timedOut
if (exitCode === 0) {
  if (timedOut) { /* 提前终止会误判为成功 */ }
}
```

### API 边界规范化

当一个实现收到同一结果的多种表示时，应在通过公共 API 返回前将其规范化。例如 `LlmAdapter.stream()` 的实现可以抛出异常或发出 `finish { kind: 'error' }`，但 `LlmRuntime.stream()` 只会通过终止型 finish 分片暴露模型请求失败。消费方不应猜测异常究竟来自哪里。

### dispose 必须完全停稳

如果清理流程只发出终止信号便返回，而不等待工作真正停止，就会留下孤儿进程。

```ts
// 正确模式
async dispose() {
  // 1. 关闭通知和监听器注册表，防止迟到的完成事件
  this._closed = true
  this._listeners.clear()
  
  // 2. 发送终止信号
  this._child.kill('SIGTERM')
  
  // 3. 等待子进程完全退出
  await this._done
}
```

### 回调异常隔离

用户提供的监听器如果抛出异常，不得导致它所在的 Promise 被 reject，也不得饿死排在它后面的监听器。

```ts
// 正确：用 try/catch 包裹分发循环
for (const listener of listeners) {
  try {
    listener(event)
  } catch (err) {
    logger.warn('监听器异常已被隔离', err)
    // 继续下一个监听器
  }
}
```

一个行为不当的订阅者绝不能破坏核心生命周期。

### 环境变量保护

启动的命令应使用经过清理的环境变量，移除名称匹配 `*KEY*`、`*SECRET*`、`*TOKEN*` 或 `*PASSWORD*` 的项，防止 harness 凭证通过命令输出、`env` 或 spill 文件泄漏。

```ts
function sanitizeEnv(env: Record<string, string>): Record<string, string> {
  const result: Record<string, string> = {}
  const sensitive = /^(.*KEY.*|.*SECRET.*|.*TOKEN.*|.*PASSWORD.*)$/i
  for (const [key, value] of Object.entries(env)) {
    if (!sensitive.test(key)) {
      result[key] = value
    }
  }
  return result
}
```

### 符号链接处理

可能是符号链接或 Windows junction 的路径，应先用 `lstatSync().isSymbolicLink()` 判断，再用 `unlinkSync` 删除：unlink 只删除链接本身并拒绝真实目录，绝不会跟随链接进入其目标。

```ts
function removeEntry(path: string) {
  const stat = fs.lstatSync(path)
  if (stat.isSymbolicLink()) {
    fs.unlinkSync(path)   // 只删除链接，不碰目标
  } else if (stat.isDirectory()) {
    fs.rmSync(path, { recursive: true })
  } else {
    fs.unlinkSync(path)
  }
}
```

## 10.8 本章小结

安全和运行时是插件开发中容易被忽视但后果最严重的领域。本章涵盖的核心要点：

1. **沙箱不是可有可无的装饰**——它是 AI 执行代码的最后一道物理隔离。三种模式（read-only、workspace-write、danger-full-access）覆盖了从审计到无限制的完整光谱，而强制执行完整性（full vs partial）让消费方可以感知边界的确切强度。

2. **策略逐调用解析**保证了并发的正确性——同一个提供方可以为不同消费方提供不同粒度的限制，已批准的提权重试不会污染后续调用的策略。

3. **权限系统将两个独立旋钮（沙箱 + 审批）捆绑为具名预设**——用户在客户端只需选择"工作区写入"或"完全访问"，而不需要理解 SandboxMode 和 ApprovalPolicy 的排列组合。

4. **会话持久化基于事件溯源**——仅追加日志是唯一真源，JSONL 和 SQLite 两种后端可互换。崩溃恢复通过合成 `interrupted` 标记保留被中断轮次的事件，绝不截断日志。

5. **压缩和 Spill 是控制会话膨胀的两把手术刀**——压缩用摘要替换历史，Spill 将超大内容外移到文件，两者都保持模型无感知。

6. **防御性编程规则来自真实的缺陷案例**——正交报告、边界规范化、停稳保证、回调隔离、环境清理和符号链接处理，每一条都对应着一次险些发布或已经发布的故障。
