## 12.1 事故 0001：ACP 服务器崩溃

**现象：** ACP（Agent Client Protocol）服务器在 Zed 编辑器连接时立即返回 `Internal Error`。第一个 `session/new` 请求报错 `cannot get property "agents" without inject`。

团队很快确认 178 个单元测试全部通过，行覆盖率 100%。为什么集成测试一片绿色，上线却直接崩溃？

**根因：** `packages/acp/acp/src/index.ts` 比别的插件多写了一行：`export default apply`。其他插件都是命名空间形式导出 `name`、`inject`、`Config`、`apply`，唯独 ACP 插件额外多了一个默认导出。当 Cordis Loader 通过 `Loader.unwrapExports` 加载模块时，代码优先选择 `.default`——结果 `apply` 函数被裸取出来，而附在模块命名空间上的 `inject: ['agents', 'sessions', 'sessionPersistence']` 全部丢失。`apply` 在一个没有注入任何服务的 fiber 中运行，第一行 `const agents = ctx.agents` 遍历整棵 fiber 树都找不到 `agents`，于是崩溃。

有意思的是，修复后暴露了第二个 bug：`session/load` 仍然在 `sessionPersistence` 上抛错。这回是 Cordis 的 shadow 代理机制在作祟——`AgentLoop.resume` 通过 shadow 代理调用时，fiber 遍历只向祖先方向进行，而 `sessionPersistence` 在一个兄弟分支上，怎么也找不到。修复方案改用 `ctx.get('sessionPersistence')`——这是一个拓扑无关的查找方法。

**为什么测试没发现？** 所有测试都使用 `ctx.plugin({ name, inject, apply })` 手动挂载插件——这直接提供了 `inject`，完全绕过了 Loader 的 `unwrapExports`。行覆盖率永远是对的，但它证明的只是代码被执行过，不是功能按交付方式正常工作。

**教训：** 命名空间插件与 `export default` 在 Cordis Loader 下互斥。至少一个测试必须端到端地驱动真实的 Loader/export 路径。相信 fiber 遍历的 `console.error` 跟踪结果，不要迷信看似合理的理论。

## 12.2 事故 0002：文件系统工具被永久禁用

**现象：** 七个文件系统场景和一个混合工作区编辑场景全部报 `UNKNOWN_TOOL` 错误。文件系统工具似乎从未注册过。

**根因：** 默认的 ACP 组合有意只启用 bash（因为其沙箱无法约束进程内的文件系统提供方），但文件系统快照场景仍然需要 `read`、`write` 和 `edit`。开发者巧妙地用 `disabled: !!js ...` 写了一个条件表达式，意图仅在快照模式下启用它们。

但 Cordis 只在插件 `config` 内部对 JavaScript 表达式求值，绝不求值 `disabled` 这样的配置项元数据。原始的表达式对象是 truthy，因此文件系统栈*在所有模式下始终处于禁用状态*。YAML 标签在语法上合法，所以加载过程不产生任何诊断信息——安静的失败才是最危险的失败。

**修复和教训：** 改为使用显式的文件系统 overlay 配置（`fs.cordis.yml`），并增加了两项守卫：`verify-cordis-config` 拒绝配置项元数据中的表达式节点；`dsh-session-snapshot` 在全新运行和已提交的会话 fixture 中拒绝结构化的 `UNKNOWN_TOOL` 结果。语法上被接受的配置值不一定在该位置被求值——务必记录并验证具体对哪些字段进行插值。

## 12.3 事故 0003：Web Agent 验收了错误的服务器

**现象：** 用户让 Web Agent 修改 GUI 主题，agent 改完源码后在端口 5173 上启动一个裸 Vite 开发服务器，看到 HTTP 200 就宣布成功。浏览器却白屏了，因为裸 Vite 不注入 `window.__DSH_BOOT__`。下一轮 agent 更离谱——它在端口 3334 上启动了一个全新的 `dsh web` 进程并验证这个替代服务，却从未检查过用户实际打开的端口 3081。

**根因：** Web 组合没有向模型提供当前 GUI 的身份信息——不知道自己的 URL、不知道是生产模式还是开发模式、不知道哪个进程在承载它。会话 cwd 正确标识了用户选择的 Workspace，但模型把这个项目目录当成了应用目录。agent 只能靠猜，每次都猜错。

修复方案让当前 URL 和运行模式对模型可见（通过 `$DSH_WEB_URL` 环境变量和系统提示词区段），在裸 Vite 开始监听前拒绝启动，并依据外部状态验收改动——不认 HTTP 200，只认用户实际看到的页面。

**教训：** Agent 必须先知道隐藏的运行时前置条件，才能指导用户。HTTP 就绪、构建成功和启动 manifest 是三个不同的事实，不能相互替代。替代服务无法证明既有页面已经改变。

## 12.4 事故 0004：Landlock 误分类

**现象：** 在 Landlock ABI 较旧的内核上，合法操作（如 ripgrep 搜索无匹配返回退出码 1）被误报为 `SANDBOX_UNAVAILABLE`。

**根因：** 问题出在一个太宽泛的签名上。Landlock launcher 在部分强制执行的旧内核上会打印一行 `landlock-run: partial enforcement (older Landlock ABI)` 然后正常执行子进程。harness 用一个不区分大小写的 `landlock-run: ` 子串匹配这两种情况，只要非零退出同时携带该子串，就归类为 runner 失败。结果子进程自己的退出码（ripgrep 无匹配返回 1）被错误地关联到 launcher 的信息性通知上。

更糟的是，当时文件系统搜索的 `runRipgrep()` 还会将捕获的任何错误替换为通用的 `SEARCH_FAILED`，其中也包括沙箱执行器产生的结构化 `SandboxUnavailableError`——双重误分类。

**修复和教训：** 进程归因需要多项独立证据同时成立：退出码 125 + 致命诊断行，而仅信息性前缀不构成故障证据。新增了 `RunnerFailureRule` 携带可选的允许退出码和精确信息性行排除规则。平台相关行为需要在原生边界放置确定性的模拟实现——会自行跳过的真实内核测试无法独自固定回归。

## 12.5 从事故中学习的通用教训

回顾这四次事故，几条教训贯穿始终：

**测试真实入口路径。** 事故 0001 中，手动构建插件的测试永远无法验证插件被 Loader 实际加载的方式。每次写测试时问自己：这个测试驱动的是真实路径还是捷径？如果是后者，再加一个端到端测试。

**行覆盖率 ≠ 行为覆盖率。** 100% 的行覆盖率仍然让两个独立 bug 同时逃逸。覆盖率只能告诉你哪行代码被执行过——不能告诉你它是否按交付方式正常工作。覆盖率的绿色勾号不是质量证明，只是最低门槛。

**平台相关行为需要确定性测试。** 事故 0004 的 Landlock 缺陷只在旧 ABI 内核上出现，而 CI 机器恰好有完整 ABI，测试静静地跳过了。如果你的特性依赖平台差异，不要依赖「恰好在那里」的环境——写一个确定性的模拟实现来固定那条路径。

**语法合法不等于语义正确。** 事故 0002 中 `!!js` 标签是合法 YAML，Cordis 愉快地解析了它——只是不求值它。配置验证守卫应该在加载时主动拒绝不可能起作用的配置。

**上下文对 Agent 不是可选项。** 事故 0003 暴露了一个根本事实：如果系统不给 Agent 提供自己的 URL 和模式，Agent 就只能猜测。任何涉及外界资源的自动化，都必须把身份信息作为一等输入提供给 Agent。

## 12.6 术语表

按拼音排序。

**Agent**
代表用户执行任务的智能体。每个 Agent 拥有独立的 scope、工具集和会话。

**Agent Loop**
Agent 的核心执行循环：接收输入 → 调用 LLM → 执行工具 → 生成响应 → 等待下一轮输入。

**Bundle**
一组预配置的插件组合，可通过 `profile` 一次加载。例如 `dsh --profile acp` 加载 ACP 服务器所需的所有插件。

**Capability Seam**
一个可替换的能力单元，由三个角色构成：Service Definition（服务定义）、Service Provider（服务提供方）和 Consumer（消费方）。参见 `dsh-shell` 的范例实现。

**Compaction**
上下文压缩机制。当对话历史超出模型窗口的阈值比例时，将早期内容压缩为摘要以节省 token。

**C（上接）ontext（ctx）**
Cordis 中的核心对象，代表插件的运行时上下文。通过 `ctx` 访问服务、注册事件监听器、管理生命周期。

**Cordis**
DeepSeek Harness 底层使用的插件化 IoC（控制反转）框架。提供 Context、Service、Event、Fiber 等核心抽象。

**effect**
Cordis 中管理副作用的原语。`ctx.effect(() => { ... })` 注册一个在插件销毁时自动清理的副作用。

**Fiber**
Cordis 中代表插件执行生命周期的轻量级单元。每个插件在加载时创建一个 fiber，负责管理其服务注入和清理。

**Function Calling**
LLM 调用预定义工具的能力。模型输出结构化 JSON 描述要调用的函数及其参数，由框架执行并将结果返回给模型。

**Goal**
附着在会话上的持久完成目标，带有 `active` / `paused` / `blocked` / `complete` 阶段和 Round 上限。

**HMR（热模块替换）**
在开发过程中无需重启整个应用即可替换运行中的插件模块。Cordis 通过文件监听和 fiber 重建实现插件级热替换。

**inject**
插件声明其依赖的服务列表。Cordis Loader 根据 `inject` 数组在 fiber 中注入对应的服务实例。

**LLM Adapter**
适配不同大语言模型提供方的插件层。每个 adapter 将统一接口映射到特定提供方（如 DeepSeek、OpenAI）的 API。

**patch**
对已加载插件配置的增量修改。在 `cordis.yml` 中通过 `patch` 关键字覆盖目标插件的配置字段。

**Plugin**
Cordis 中的基本可加载单元。一个插件由 `name`、`inject`、`Config` 和 `apply` 函数组成，注册到 Context 上。

**Profile**
预定义的启动配置组合。通过 `dsh --profile <name>` 指定，决定加载哪些插件及其配置。

**Sandbox**
受限执行环境。DeepSeek Harness 支持多种沙箱实现：Landlock（Linux 本地）、bwrap（Bubblewrap）、Seatbelt（macOS）、E2B（远程）。

**Scope**
按 Agent 划分的注册单位。工具、提示词段、变量要么是全局的（对所有 Agent 可见），要么是带作用域的（归属于唯一一个 scope key）。

**Seam（能力缝）**
参见 Capability Seam。

**Session**
一次 Agent 对话的持久化记录。包含消息历史、工具调用记录、元数据等，可通过 ID 恢复。

**Spill**
当工具输出超过内存上限时溢出到临时文件的机制。`maxOutputBytes` 和 `maxSpillBytes` 控制溢出阈值。

**Step**
Agent Loop 中的一次模型请求及由此引发的工具执行序列。一个 Turn 包含零到多个 Step。

**Subagent**
由当前 Agent 委派执行子任务的子 Agent。通过 `subagent` 工具创建，拥有独立的 scope 和会话。

**Tool**
Agent 可调用的具名功能。每个 Tool 定义 JSON Schema 参数列表，由 LLM 通过 Function Calling 调用。

**Turn**
会话中一次对已接纳输入的排空过程。从用户输入开始，到模型停止生成工具调用或触发终止策略结束。

**Waterfall**
事件在 Cordis fiber 树中向上冒泡的分发模式。子 fiber 的事件沿祖先路径传播到父 fiber。
